# آشنایی با Kotlin Multiplatform؛ توسعه چندسکویی با یک زبان

Kotlin Multiplatform یکی از فناوری‌های قدرتمند اکوسیستم Kotlin است که امکان اشتراک‌گذاری کد میان پلتفرم‌های مختلف را فراهم می‌کند. با استفاده از این فناوری می‌توان بخش‌هایی از منطق برنامه را یک‌بار پیاده‌سازی کرد و در چند پلتفرم از آن‌ها استفاده کرد؛ بدون اینکه انعطاف‌پذیری توسعه بومی (Native) از بین برود.

در این مقاله با مفاهیم اصلی Kotlin Multiplatform، معماری آن، مزایا، ساختار پروژه و کاربردهای عملی آن آشنا می‌شویم.

![نمایی از معماری Kotlin Multiplatform](images/kotlin-multiplatform/kmp-architecture.png)

## Kotlin Multiplatform چیست؟

Kotlin Multiplatform که به اختصار KMP نامیده می‌شود، فناوری‌ای برای اشتراک‌گذاری کد میان پلتفرم‌هایی مانند Android، iOS، Desktop و Web است.

برخلاف رویکردهایی که کل رابط کاربری و منطق برنامه را به یک لایه مشترک محدود می‌کنند، KMP به توسعه‌دهنده اجازه می‌دهد تصمیم بگیرد کدام قسمت‌ها مشترک باشند و کدام قسمت‌ها به‌صورت اختصاصی برای هر پلتفرم پیاده‌سازی شوند.

برای مثال، می‌توان بخش‌های زیر را میان پلتفرم‌ها به اشتراک گذاشت:

- منطق تجاری برنامه (Business Logic)
- ارتباط با سرویس‌های شبکه
- مدیریت داده‌ها و پایگاه داده
- مدل‌ها و اعتبارسنجی اطلاعات
- بخش‌هایی از منطق رابط کاربری

## معماری Kotlin Multiplatform

یکی از مفاهیم مهم در KMP، تفکیک کد مشترک از کد اختصاصی پلتفرم‌ها است.

ساختار معمول یک پروژه شامل دو بخش اصلی است:

### کد مشترک (Common Code)

کدهایی که مستقل از پلتفرم هستند در Source Set مشترک قرار می‌گیرند. این بخش می‌تواند شامل مدل‌ها، Use Caseها، Repositoryها و منطق اصلی برنامه باشد.

### کد اختصاصی پلتفرم (Platform-specific Code)

در مواردی که هر سیستم‌عامل به پیاده‌سازی متفاوتی نیاز دارد، می‌توان کد اختصاصی همان پلتفرم را نوشت.

برای نمونه، دسترسی به قابلیت‌های خاص Android یا iOS می‌تواند در Source Set مربوط به همان پلتفرم قرار بگیرد.

![ساختار Source Set در Kotlin Multiplatform](images/kotlin-multiplatform/kmp-source-sets.png)

## مفهوم expect و actual

Kotlin Multiplatform برای مدیریت تفاوت‌های میان پلتفرم‌ها از مکانیزم `expect` و `actual` استفاده می‌کند.

با `expect` یک قرارداد در کد مشترک تعریف می‌کنیم و با `actual` پیاده‌سازی متناسب با هر پلتفرم را ارائه می‌دهیم.

برای مثال، فرض کنیم برنامه به نام سیستم‌عامل نیاز دارد.

ابتدا در کد مشترک:

```kotlin
expect fun getPlatformName(): String
```

سپس در پیاده‌سازی Android:

```kotlin
actual fun getPlatformName(): String = "Android"
```

و در پیاده‌سازی Desktop:

```kotlin
actual fun getPlatformName(): String = "Desktop"
```

به این ترتیب، کد مشترک بدون اطلاع از جزئیات پیاده‌سازی هر پلتفرم می‌تواند از این تابع استفاده کند.

## ساختار یک پروژه KMP

یک پروژه Kotlin Multiplatform معمولاً از چند Source Set تشکیل می‌شود که هرکدام مسئول نگهداری کدهای یک محدوده مشخص هستند.

ساختار ساده‌شده یک پروژه می‌تواند به شکل زیر باشد:

```text
shared/
└── src/
    ├── commonMain/
    │   └── kotlin/
    │       ├── data/
    │       ├── domain/
    │       └── presentation/
    │
    ├── androidMain/
    │   └── kotlin/
    │
    ├── iosMain/
    │   └── kotlin/
    │
    └── desktopMain/
        └── kotlin/
```

- `commonMain`: کدهای مشترک میان پلتفرم‌ها
- `androidMain`: پیاده‌سازی‌های اختصاصی Android
- `iosMain`: پیاده‌سازی‌های اختصاصی iOS
- `desktopMain`: پیاده‌سازی‌های اختصاصی Desktop

این ساختار بسته به پلتفرم‌های هدف و معماری پروژه می‌تواند متفاوت باشد.

## Kotlin Multiplatform و Compose Multiplatform

این دو فناوری ارتباط نزدیکی با یکدیگر دارند، اما یکسان نیستند.

**Kotlin Multiplatform** امکان اشتراک‌گذاری کد و منطق برنامه را فراهم می‌کند.

**Compose Multiplatform** چارچوبی مبتنی بر Jetpack Compose است که امکان ساخت رابط کاربری مشترک برای چند پلتفرم را فراهم می‌کند.

در نتیجه، می‌توان با ترکیب این دو فناوری، هم منطق برنامه و هم بخش زیادی از رابط کاربری را میان پلتفرم‌ها به اشتراک گذاشت.

## مزایای Kotlin Multiplatform

### ۱. کاهش تکرار کد

منطق مشترک فقط یک‌بار نوشته می‌شود و در پلتفرم‌های مختلف مورد استفاده قرار می‌گیرد. این موضوع نگهداری و توسعه پروژه را ساده‌تر می‌کند.

### ۲. استفاده از قابلیت‌های بومی

توسعه‌دهنده همچنان می‌تواند به APIها و قابلیت‌های اختصاصی هر پلتفرم دسترسی داشته باشد.

### ۳. اشتراک‌گذاری تدریجی

نیازی نیست تمام برنامه از ابتدا به KMP منتقل شود. می‌توان ابتدا یک بخش کوچک مانند منطق شبکه یا مدیریت داده را مشترک کرد و به‌مرور دامنه اشتراک‌گذاری را گسترش داد.

### ۴. استفاده از اکوسیستم Kotlin

امکان استفاده از کتابخانه‌ها و ابزارهای شناخته‌شده Kotlin مانند Coroutines، Flow و کتابخانه‌های چندسکویی فراهم است.

## چالش‌های توسعه با KMP

با وجود مزایای متعدد، توسعه چندسکویی بدون چالش نیست.

- **تفاوت APIهای پلتفرم‌ها:** برخی قابلیت‌ها نیازمند پیاده‌سازی اختصاصی هستند.
- **مدیریت وابستگی‌ها:** باید از کتابخانه‌هایی استفاده کرد که پلتفرم‌های موردنظر را پشتیبانی می‌کنند.
- **ساخت و انتشار:** تنظیمات Build و فرآیند انتشار در هر پلتفرم می‌تواند متفاوت باشد.
- **آزمایش و اشکال‌زدایی:** رفتار برنامه باید در محیط‌های هدف بررسی شود.

بنابراین، انتخاب معماری و کتابخانه‌های مناسب از ابتدای پروژه اهمیت زیادی دارد.

## چه زمانی از Kotlin Multiplatform استفاده کنیم؟

KMP زمانی انتخاب مناسبی است که بخواهیم منطق اصلی برنامه را میان چند پلتفرم به اشتراک بگذاریم، اما همچنان کنترل و انعطاف‌پذیری توسعه بومی را حفظ کنیم.

این فناوری به‌خصوص برای پروژه‌هایی مناسب است که:

- نسخه Android و iOS دارند.
- منطق تجاری پیچیده و مشترکی دارند.
- به نگهداری و توسعه بلندمدت نیاز دارند.
- می‌خواهند به‌تدریج از کد مشترک استفاده کنند.

البته اگر پروژه فقط برای یک پلتفرم ساخته می‌شود، استفاده از KMP لزوماً مزیت خاصی ایجاد نمی‌کند.

## جمع‌بندی

Kotlin Multiplatform رویکردی انعطاف‌پذیر برای توسعه نرم‌افزار در چند پلتفرم است. این فناوری به توسعه‌دهندگان اجازه می‌دهد بدون کنار گذاشتن قابلیت‌های بومی، بخش‌های مهم برنامه را به اشتراک بگذارند.

ترکیب KMP با معماری مناسب و ابزارهایی مانند Compose Multiplatform می‌تواند فرایند توسعه، نگهداری و گسترش برنامه‌ها را ساده‌تر کند.

مهم‌ترین نکته این است که KMP قرار نیست همه‌چیز را مشترک کند؛ هدف آن اشتراک‌گذاری هوشمندانه بخش‌هایی است که واقعاً به اشتراک‌گذاری نیاز دارند.
